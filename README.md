# Thesis files & scripts

Code & Dataset repository of the thesis. This repository contains the datasets, evasion payloads, automation pipelines, and feasibility experiments developed to evaluate LLM-guided dynamic resolution of API hashing.

## Repository Structure and Generation Workflow

The repository is divided into distinct folders that represent the data generation and evaluation phases of the research.

### 1. Algorithms (`algorithms/`)
This directory contains the raw Python and C implementations of the hashing algorithms used to build the dataset.
* `py-to-c-algos-gemini/`: Contains 105 standard algorithms. These were sourced from the public OALabs HashDB repository (originally in Python) and translated into C code utilizing the `gemini_converter_py_to_c.py` script via the Gemini 1.5-Flash API.
* `custom_hash_algorithms/`: Contains 9 novel algorithms designed to bypass static signature databases. This is subdivided into:
    * `custom-new-human/`: Algorithms manually authored using low-level primitives (e.g., PS-32, RA-32).
    * `custom-new-llm/`: Highly complex cryptographic algorithms generated entirely by an LLM.
    * `modified/`: Standard HashDB algorithms that have been mutated with custom seeds or post-calculation shifts.

### 2. Automation Pipeline (`pipeline_scripts/`)
This directory contains the Python scripts responsible for translating algorithms and building the final malware executables.
* `gemini_converter_py_to_c.py`: Connects to the Gemini API to automatically translate the Python-based HashDB algorithms into C code prior to compilation.
* `generator.py`: Targets the 105 standard baseline algorithms (Phase 1). It reads the LLM-translated C files and their original Python pairs from the `algorithms/py-to-c-algos-gemini/` folder.
* `generator_new_algos.py`: Targets the 9 custom algorithms (Phase 2). It skips the LLM translation step and reads the manually created Python and C pairs directly from the `algorithms/custom_hash_algorithms/` subfolders.

For both generator scripts, the core execution flow is identical:
* Differential Fuzzing: Feed random strings into both the Python and C versions of an algorithm to guarantee mathematical equivalence.
* Injection: Inject the verified C logic and pre-calculated target hashes into the freestanding C loader template.
* Compilation: Compile the payload using MinGW with the `-nostdlib` flag to remove the standard Import Address Table (IAT).
* Output: Output the fully compiled, functional `.exe` payloads and their source `.c` files to the `templates/working-templates/` directory.

### 3. Compiled Output (`templates/working-templates/`)
This directory holds the 115 successfully compiled executables generated by the pipeline scripts, ready for static and dynamic analysis testing.

### 4. Evasive Ground Truth (`evasion_payloads/`)
Contains `evade_speakeasy.c`, a custom malware template engineered to defeat standard emulators. It wraps a standard hashing algorithm in anti-analysis guardrails, specifically utilizing massive API flooding loops and hardware artifact checks.

### 5. Feasibility Pilot (`pilot/`)
Contains three Ghidra scripts and their results, used to validate the architecture of the proposed tool before implementation. They test whether emulating a malware resolver in isolation fails on a real sample, and whether provisioning a minimal process environment makes the same resolver succeed.

* `PilotA.java`: Emulates a real module resolver with no process environment provisioned. The resolver reads its PEB pointer, receives zero, and returns after 16 instructions. The failure is silent rather than a fault, which is indistinguishable from an unresolvable hash.
* `PilotB.java`: Provisions a PEB, loader data, and a two-entry module list, then resolves a module by hash. Succeeds using 98 bytes of synthesised process state and one intercepted call. The target hash is computed by executing the sample's own hash function rather than read from a database.
* `PilotC.java`: Maps the PE headers and export data region of a real system library from disk, then resolves an API hash taken from the sample's own call sites. Succeeds using 84,277 bytes, or 4.6% of the library file. No candidate list is supplied; candidate names are read from the library's own export table.

`pilot/README.md` documents the method, the raw output of each run, and what the results mean. It also covers how to install and run a Ghidra script, and how to prepare the DLL corpus that `PilotC.java` reads from.

### 6. Ghidra MCP Extension (`ghidra_mcp_extension/`)
Staging area for files intended for a future fork of Benjamin Ethington's `ghidra-mcp` repository. The resolution module itself will be released in that fork rather than here, since it extends an existing codebase.
