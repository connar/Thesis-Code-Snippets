# Thesis code and data

Code and data for my MSc thesis on resolving API hashes in Windows malware with
an LLM agent and Ghidra.

The resolver itself is not in this repository. It is a branch of a fork of
`ghidra-mcp`: https://github.com/connar/ghidra-mcp/tree/api-hash-resolver

## Folders

### `algorithms/`

Hash algorithms used to build the test loaders, each as a Python and a C
version.

- `py-to-c-algos-gemini/`: 104 algorithms taken from the OALabs HashDB
  repository, which publishes them in Python. The C versions were produced by
  Gemini (`gemini-2.5-flash`) with `pipeline_scripts/gemini_converter_py_to_c.py`.
  They are left exactly as generated, since they are part of the experiment.
- `custom_hash_algorithms/`: 9 algorithms that HashDB does not have.
  - `custom-new-human/`: 3 algorithms I wrote by hand (PS-32, RA-32, SAX-32).
  - `custom-new-llm/`: 3 algorithms generated by an LLM, with its descriptions.
  - `modified/`: 3 HashDB algorithms changed with a different seed or an extra
    step after hashing.

### `pipeline_scripts/`

- `gemini_converter_py_to_c.py`: sends each Python algorithm to Gemini and saves
  the C version it returns.
- `generator.py`: builds a loader for each of the HashDB algorithms.
- `generator_new_algos.py`: the same for the 9 custom algorithms, which already
  have a C version, so no conversion step.

For each algorithm, a generator:

1. computes the hashes of the target API names with the Python version,
2. puts the C version and those hashes into `templates/loader_template.c`,
3. compiles it with MinGW and `-nostdlib`, so the loader finds its APIs by hash
   instead of through the import table,
4. runs it and counts it as working only if it launches Calculator. That only
   happens if the C hash produces the same values as the Python one.

### `templates/`

- `loader_template.c`: the loader the generators fill in.
- `working-templates/`: the source of the 113 loaders that passed step 4. The
  compiled `.exe` files are not committed.

### `evasion_payloads/`

`evade_speakeasy.c`: a loader built to avoid analysis in Speakeasy. Before doing
anything it calls `GetCurrentProcessId` about 325,000 times, and it exits if the
system reports zero processors, which an emulator can report but a real machine
cannot. It resolves its APIs by hash like the other loaders. The write-up is at
https://i0.rs/blog/bypassing-speak-easy/

### `pilot/`

Three Ghidra scripts run before the resolver was built, to check that the idea
works on a real sample.

- `PilotA.java`: emulates a real module resolver with nothing set up. It reads
  a PEB pointer of zero and returns after 16 instructions without an error, so
  the failure looks the same as a hash that does not resolve.
- `PilotB.java`: sets up a PEB, loader data and a two-entry module list, then
  resolves a module by hash. It needs 98 bytes of process state and one
  intercepted call. The target hash comes from running the sample's own hash
  function.
- `PilotC.java`: maps the headers and export data of a real system DLL from
  disk and resolves an API hash taken from the sample's call sites. It needs
  84,277 bytes, 4.6% of the DLL. The candidate names come from the DLL's own
  export table.

`pilot/README.md` has the method, the raw output of each run, and how to run
the scripts in Ghidra.

### `ground_truth/`

The ground truth used to score the resolver on the ten evaluation samples, and
the script that compares the resolver's output against it. See
`ground_truth/README.md`.
